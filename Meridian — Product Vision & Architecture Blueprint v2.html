01 — The Problem

The gap that creates this product

Twelve years of strategy and management consulting produces a very specific frustration. It is not that the analyses are hard. The frameworks — pocket price waterfall, CLTV cohort, margin bridge, churn propensity — are well understood by any manager who has run a commercial engagement. The frustration is structural: the person who understands the business question is almost never the same person who can execute the analysis.

This is not a spreadsheet limitation. Excel is not the bottleneck. The bottleneck is infrastructure setup time, analyst queue lag, and the fact that SQL, Python, Tableau, Alteryx, and enterprise pricing tools sit behind access walls — institutional licences, data engineering pipelines, and analyst pools that only large consulting teams or enterprise clients can afford.

The access gap: MBA-trained strategy professionals carry the analytical intelligence to ask the right questions. They lack the infrastructure to answer them independently. The result is either expensive teaming overhead, a weeks-long queue, or the question never getting answered rigorously at all.

Two engagements that made this concrete

At Monitor Deloitte, a ~$50M pricing transformation for a US auto parts retailer required a dedicated analytics stack — SQL Server, Alteryx pipelines, Tableau dashboards — to isolate pocket price leakage across 200,000 SKUs. The analytical logic was clear within days. Getting clean, segmented data into the right shape took weeks of analyst time and infrastructure coordination.

At Mahindra, a multi-million customer dataset running on SQL Server with a dedicated consumer analytics pool produced CLTV models, propensity scores, and churn signals that were genuinely decision-relevant. But every iteration — every "what if we segment by tractor use case rather than region?" — went back into the queue. The insight was delayed by infrastructure, not thinking.

Meridian is the answer to both of those situations.

02 — Product Vision

A virtual consulting analyst. In a browser tab.

Meridian is a suite of browser-native analytical modules, unified by a single data ingestion and ETL engine (Meridian Bridge), each module purpose-built for a specific engagement archetype a strategy consultant would recognise immediately.

The goal is not to replace the consultant. It is to eliminate the separation between strategic understanding and analytical execution — so the manager who knows what question to ask can answer it, without assembling a team, standing up infrastructure, or procuring a licence.

The capstone proposition: Strategy consulting managers get leaner, faster teaming structures. SMEs and growth-stage businesses get consulting-grade analytics they could not otherwise afford. Both get the same outcome: from raw dataset to boardroom-ready diagnostic, in a single session, in a browser. No code. No licence. No data leaves the machine.

Four strategic bets — unchanged

B1

Business brain, not engineering brain

Every UI decision, analytical frame, and label is designed for someone who thinks in business terms — engagement manager, commercial lead, brand P&L owner. Never for a data scientist.

B2

Full workflow coverage

A tool that stops at the chart is half a tool. Every module covers the complete arc: data ingestion → transformation → analysis → diagnostic output → export-ready deliverable. Output is paste-able into a board deck without reformatting.

B3

Zero-server architecture

No server ever sees the user's data. An architectural fact, not a marketing claim. All computation runs in-browser: Vanilla JS, Web Workers, Pyodide (WASM Python).

B4

Open-source consulting IP

The analytical frameworks embedded in each module are real — drawn from commercial engagements. Build-in-public on GitHub means methodology is transparent and forkable.

05 — Platform Architecture

Hub and spoke. Canvas-first. Pipeline-aware.

Meridian Bridge (the DataBridge ETL core) is the platform hub. Every analytical module is a downstream spoke. The interaction layer offers two views for every workflow: a canvas view (Alteryx-style drag-drop node graph) and a panel view (the current step-by-step UI). Both produce identical outputs. The user switches between them freely.

L1

Platform core — Meridian Bridge

All data ingestion, ETL pipeline, quality scoring, schema mapping, module routing. Produces the standardised AppHandoff payload consumed by every module.

L2

Module layer — engagement-specific analytical tools

Each module is a standalone HTML file. Receives the AppHandoff payload, runs its own analytical logic, produces export-ready outputs. No inter-module dependencies.

L3

Canvas layer — unified workflow view

An optional interaction mode that exposes the full platform as a node graph. ETL operations, schema mapping, analytical modules, and export steps are all nodes. The user connects them by drawing edges. The canvas is the pipeline.

L4

Pipeline layer — save, name, replay

Any workflow — in canvas or panel view — can be saved as a named pipeline. Pipelines store the full node configuration and schema map, not the data. Loaded on a new dataset, they replay the same analysis with zero reconfiguration.

L5

Compute layer — tiered by complexity

Vanilla JS for light analytics, Web Workers for heavy tabular operations (>10K rows), Pyodide (WebAssembly Python) for ML model inference. No server call at any tier.

07 — Canvas System

Alteryx-style drag-drop, across the full platform

The canvas is not a feature added on top of the platform. It is an alternative interaction layer for the entire platform — from raw data ingestion through ETL transformation through analytical module through export. Every operation that exists in the panel UI also exists as a canvas node. The canvas is the pipeline, made visible.

Design principle: Canvas and panel UI are two views of the same underlying data model. Switching from panel to canvas mid-workflow does not reset progress. The nodes on the canvas are the steps the user already configured in the panel. They are the same thing, rendered differently.

Node types

⊞
source

Data source nodes

CSV upload, XLSX upload, demo dataset, sessionStorage receive. One per workflow.

⟳
transform

ETL operation nodes

Filter, aggregate, join, pivot, calculate, bin, rank, lag/lead. The full Bridge operation set.

◈
map

Schema map nodes

Maps columns to analytical dimensions. One per module destination. Required before any analysis node.

⬟
analyse

Analysis nodes

One per analytical output — Pocket Price Waterfall, CLTV Model, Margin Bridge, Churn Score, etc.

◎
visualise

Visualisation nodes

Chart, table, summary card. Connect to analysis nodes. Multiple visualisation nodes can read the same analysis output.

↗
export

Export nodes

PDF report, XLSX data, PNG chart. Terminal nodes — no outgoing edges. Multiple allowed per workflow.

Canvas interaction model

Node palette sidebar

All available nodes organised by category. Drag onto canvas to place. Nodes show required input ports and available output ports. Incompatible connections are rejected with an inline error.

Edge drawing

Click an output port, drag to an input port to connect. Edges carry typed data — a schema-mapped output cannot connect to an analysis node with incompatible dimension requirements. Type mismatches shown visually.

Node configuration panel

Click any node to open its configuration in a side panel — the same UI as the panel view equivalent. Canvas and panel view share the same configuration component code.

Run button

Executes the full workflow from source to export nodes. Nodes light up sequentially as they complete. Errors surface inline on the node that failed. No silent failures.

08 — Reusable Pipelines

Build once. Run every month.

A pipeline is a named, saved workflow — the full graph of nodes, edges, and configurations, without the data. Loading a pipeline on a new dataset replays the entire workflow: the same transformations, the same schema mapping, the same analytical frames, the same export format. The only variable is the data.

localStorage (default)

Pipelines save automatically to the browser's localStorage under the meridian_pipelines key. They persist across sessions on the same machine. The pipeline library shows all saved pipelines with name, last-run date, and module target.

JSON export (portable backup)

Any pipeline can be exported as a .meridian JSON file. This file can be shared with a colleague, stored in a client folder, or version-controlled in a repo. Re-imported via the pipeline library in one click.

Pipeline data model

// A saved pipeline — what gets written to localStorage / JSON
{
  id:          "pipe_monthly_pricing_rev",
  name:        "Monthly Pricing Review — Renova",
  module:      "price",
  createdAt:   "2025-10-01T09:00:00Z",
  lastRunAt:   "2025-11-01T08:45:00Z",
  nodes: [
    { id: "n1", type: "source", config: { mode: "upload" } },
    { id: "n2", type: "filter", config: { expr: "[year] == 2024 AND [return_flag] == 0" } },
    { id: "n3", type: "calculate", config: { col: "pocket_price", expr: "[list_price] - [disc_amt]" } },
    { id: "n4", type: "schemaMap", config: { module: "price", map: { listPrice: "list_price", pocketPrice: "pocket_price" } } },
    { id: "n5", type: "analysis", config: { analysis: "pocket_price_waterfall" } },
    { id: "n6", type: "export", config: { format: "pdf", filename: "pricing_review_{date}" } }
  ],
  edges: [
    { from: "n1", to: "n2" }, { from: "n2", to: "n3" },
    { from: "n3", to: "n4" }, { from: "n4", to: "n5" },
    { from: "n5", to: "n6" }
  ]
  // No data — only the configuration. Data loads fresh each run.
}

What makes a pipeline portable: Because a pipeline stores node configurations and schema maps — never data — a .meridian file can be shared freely. A consulting manager can share their "Monthly Board Update" pipeline with a client's chief of staff. The client loads their own data. The analysis runs identically. This is consulting IP as a reusable workflow.

09 — AppHandoff Protocol

The interface contract between core and modules

Defined once, consumed by all. Any module that implements the receiver gets a fully prepared, quality-scored, schema-mapped dataset — without knowing what upstream operations produced it.

// AppHandoff — written to sessionStorage by Meridian Bridge
// key: 'meridian_handoff'
{
  source:       "Meridian Bridge",
  targetModule: "pulse",          // price | pulse | ledger | org | field | flow
  pipelineId:   "pipe_monthly_...", // null if ad-hoc
  sentAt:       "2025-11-01T08:45:00Z",
  rowCount:     45231,
  columns:      ["customer_id", "revenue_ltm", "last_purchase_date", ...],
  columnTypes:  { "customer_id": "id", "revenue_ltm": "number", ... },
  schema:       { "customerId": "customer_id", "revenue": "revenue_ltm", ... },
  qualityScore: 0.94,
  rows:         [{ ... }, { ... }]
}

Every module implements the four-method receiver interface: receiveHandoff(payload) → validateSchema(schema, required) → initModule(rows, schema) → renderOutputs(). Modules requiring Pyodide add a fifth: initPyodide() called asynchronously before initModule.

10 — Compute Model

Three tiers. Zero server. Full Python.

Vanilla JS
Aggregations, ratios, waterfall construction, sorting, filtering, basic statistics. Under 10K rows. Synchronous, instant. All modules, always.
All modules
Web Workers
Heavy tabular operations on datasets over 10K rows. Off main thread, non-blocking UI. Canvas pipeline execution also runs in a Worker.
>10K rows
Pyodide
Full Python runtime via WebAssembly. NumPy, pandas, scikit-learn, scipy, lifetimes. CLTV (BG/NBD), churn (logistic regression), propensity (gradient boosting), k-means clustering, ARIMA demand forecasting, survival analysis. Loads once, stays warm per session.
Pulse, Ledger, Org, Field, Flow · ML analyses

Scale ceiling: 50K rows is the comfortable zone for all analysis types including ML inference. The architecture scales to 500K rows for ETL/aggregations and 200K rows for churn/propensity inference without any architectural change — only a chunked file parser (already supported by PapaParse streaming mode) and mini-batch model variants. No server required at any scale within the defined operating range.

13 — Design Principles

Eight principles — updated for canvas and pipelines

P1

The framework is the UI

Each module's interface is shaped by the analytical framework it embodies. The output is recognisable before the user reads a label.

P2

Canvas and panel are the same workflow

Switching views mid-workflow does not reset progress. The canvas renders the panel's state as nodes; the panel renders the canvas's state as steps. They are two representations of one data model.

P3

Schema mapping before analysis, always

No module runs analysis on unmapped data. The schema wizard is not skippable. This enforces methodological consistency — the output is always a real pocket price waterfall, not a chart on user data that someone labelled one.

P4

Outputs are deliverable-ready, not exploration-ready

The export target is a board deck or client presentation. Charts use consulting-grade colour and labelling. Tables include the metadata a reviewer needs. PDF export is a first-class feature.

P5

Complexity is hidden, not removed

BG/NBD and ARIMA run under the hood. The user sees the business output. Power users can inspect model parameters; everyone else gets the answer.

P6

Data never leaves the machine

Stated in every module's header as a factual architectural statement. This is also what makes the platform viable for consulting use — client data can be analysed locally without data governance implications.

P7

Each module is independently launchable

A module can receive a Bridge handoff or accept a direct upload. A user can bookmark Meridian Pulse, go directly to it, upload a CSV, and run a CLTV analysis — without opening Bridge at all.

P8

Pipelines are first-class IP

A saved pipeline is a consulting deliverable. It encodes the analytical methodology — the transformations, the schema map, the analytical frame — in a portable, reusable format. Sharing a .meridian file is sharing a workflow, not just data.

16 — Constraints & Scope Boundary

What Meridian is not

Immutable constraints: Zero server. Zero licence. Zero data leaves the user's machine. Single HTML file per module. CDN-only dependencies. These are architectural commitments. Any feature that violates them is out of scope by definition, regardless of how it is requested.

Explicit out-of-scope for v1.0

User accounts and cloud sync — no backend means no account system. Pipelines persist in localStorage and export as JSON. That is the persistence model.

Real-time data connections — no API integrations, no live database connections. Input is always a file upload or sessionStorage handoff.

Collaborative editing — one user, one browser session. Pipeline sharing is via .meridian file export, not a shared workspace.

Custom model training — Pyodide runs inference on pre-defined model architectures. Users cannot upload custom weights or modify model architectures. The ML layer is intentionally black-boxed.

Mobile-first design — desktop and laptop primary. Analytical tools at this complexity require screen real estate. Responsive layouts implemented, mobile not the primary experience.

The capstone outcome: When all six modules are live, Meridian will be the most comprehensive open-source browser-native analytical workbench for strategy and commercial consulting practitioners in existence. Alteryx-style canvas workflows. Reusable pipelines as shareable consulting IP. Full ML inference in-browser. Every module grounded in real engagement experience. Zero infrastructure. Permanent open access.
