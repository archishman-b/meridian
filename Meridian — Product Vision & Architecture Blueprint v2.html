01 — The Problem

The gap that creates this product

Twelve years of strategy and management consulting produces a very specific frustration. It is not that the analyses are hard. The frameworks — pocket price waterfall, CLTV cohort, margin bridge, churn propensity — are well understood by any manager who has run a commercial engagement. The frustration is structural: the person who understands the business question is almost never the same person who can execute the analysis.

This is not a spreadsheet limitation. Excel is not the bottleneck. The bottleneck is infrastructure setup time, analyst queue lag, and the fact that SQL, Python, Tableau, Alteryx, and enterprise pricing tools sit behind access walls — institutional licences, data engineering pipelines, and analyst pools that only large consulting teams or enterprise clients can afford.

The access gap: MBA-trained strategy professionals carry the analytical intelligence to ask the right questions. They lack the infrastructure to answer them independently. The result is either expensive teaming overhead, a weeks-long queue, or the question never getting answered rigorously at all.

Two engagements that made this concrete

At Monitor Deloitte, a ~$50M pricing transformation for a US auto parts retailer required a dedicated analytics stack — SQL Server, Alteryx pipelines, Tableau dashboards — to isolate pocket price leakage across 200,000 SKUs. The analytical logic was clear within days. Getting clean, segmented data into the right shape took weeks of analyst time and infrastructure coordination.

At Mahindra, a multi-million customer dataset running on SQL Server with a dedicated consumer analytics pool produced CLTV models, propensity scores, and churn signals that were genuinely decision-relevant. But every iteration — every "what if we segment by tractor use case rather than region?" — went back into the queue. The insight was delayed by infrastructure, not thinking.

Meridian is the answer to both of those situations.

02 — Product Vision

A virtual consulting analyst. In a browser tab.

Meridian is a suite of browser-native analytical modules, unified by a single data ingestion and ETL engine (Meridian Bridge), each module purpose-built for a specific engagement archetype a strategy consultant would recognise immediately.

The goal is not to replace the consultant. It is to eliminate the separation between strategic understanding and analytical execution — so the manager who knows what question to ask can answer it, without assembling a team, standing up infrastructure, or procuring a licence.

The capstone proposition: Strategy consulting managers get leaner, faster teaming structures. SMEs and growth-stage businesses get consulting-grade analytics they could not otherwise afford. Both get the same outcome: from raw dataset to boardroom-ready diagnostic, in a single session, in a browser. No code. No licence. No data leaves the machine.

Four strategic bets — unchanged

B1

Business brain, not engineering brain

Every UI decision, analytical frame, and label is designed for someone who thinks in business terms — engagement manager, commercial lead, brand P&L owner. Never for a data scientist.

B2

Full workflow coverage

A tool that stops at the chart is half a tool. Every module covers the complete arc: data ingestion → transformation → analysis → diagnostic output → export-ready deliverable. Output is paste-able into a board deck without reformatting.

B3

Zero-server architecture

No server ever sees the user's data. An architectural fact, not a marketing claim. All computation runs in-browser: Vanilla JS, Web Workers, Pyodide (WASM Python).

B4

Open-source consulting IP

The analytical frameworks embedded in each module are real — drawn from commercial engagements. Build-in-public on GitHub means methodology is transparent and forkable.

05 — Platform Architecture

Hub and spoke. Canvas-first. Pipeline-aware.

Meridian Bridge (the DataBridge ETL core) is the platform hub. Every analytical module is a downstream spoke. The interaction layer offers two views for every workflow: a canvas view (Alteryx-style drag-drop node graph) and a panel view (the current step-by-step UI). Both produce identical outputs. The user switches between them freely.

L1

Platform core — Meridian Bridge

All data ingestion, ETL pipeline, quality scoring, schema mapping, module routing. Produces the standardised AppHandoff payload consumed by every module.

L2

Module layer — engagement-specific analytical tools

Each module is a standalone HTML file. Receives the AppHandoff payload, runs its own analytical logic, produces export-ready outputs. No inter-module dependencies.

L3

Canvas layer — unified workflow view

An optional interaction mode that exposes the full platform as a node graph. ETL operations, schema mapping, analytical modules, and export steps are all nodes. The user connects them by drawing edges. The canvas is the pipeline.

L4

Pipeline layer — save, name, replay

Any workflow — in canvas or panel view — can be saved as a named pipeline. Pipelines store the full node configuration and schema map, not the data. Loaded on a new dataset, they replay the same analysis with zero reconfiguration.

L5

Compute layer — tiered by complexity

Vanilla JS for light analytics, Web Workers for heavy tabular operations (>10K rows), Pyodide (WebAssembly Python) for ML model inference. No server call at any tier.

07 — Canvas System

Alteryx-style drag-drop, across the full platform

The canvas is not a feature added on top of the platform. It is an alternative interaction layer for the entire platform — from raw data ingestion through ETL transformation through analytical module through export. Every operation that exists in the panel UI also exists as a canvas node. The canvas is the pipeline, made visible.

Design principle: Canvas and panel UI are two views of the same underlying data model. Switching from panel to canvas mid-workflow does not reset progress. The nodes on the canvas are the steps the user already configured in the panel. They are the same thing, rendered differently.

Node types

⊞
source

Data source nodes

CSV upload, XLSX upload, demo dataset, sessionStorage receive. One per workflow.

⟳
transform

ETL operation nodes

Filter, aggregate, join, pivot, calculate, bin, rank, lag/lead. The full Bridge operation set.

◈
map

Schema map nodes

Maps columns to analytical dimensions. One per module destination. Required before any analysis node.

⬟
analyse

Analysis nodes

One per analytical output — Pocket Price Waterfall, CLTV Model, Margin Bridge, Churn Score, etc.

◎
visualise

Visualisation nodes

Chart, table, summary card. Connect to analysis nodes. Multiple visualisation nodes can read the same analysis output.

↗
export

Export nodes

PDF report, XLSX data, PNG chart. Terminal nodes — no outgoing edges. Multiple allowed per workflow.

Canvas interaction model

Node palette sidebar

All available nodes organised by category. Drag onto canvas to place. Nodes show required input ports and available output ports. Incompatible connections are rejected with an inline error.

Edge drawing

Click an output port, drag to an input port to connect. Edges carry typed data — a schema-mapped output cannot connect to an analysis node with incompatible dimension requirements. Type mismatches shown visually.

Node configuration panel

Click any node to open its configuration in a side panel — the same UI as the panel view equivalent. Canvas and panel view share the same configuration component code.

Run button

Executes the full workflow from source to export nodes. Nodes light up sequentially as they complete. Errors surface inline on the node that failed. No silent failures.

08 — Reusable Pipelines

Build once. Run every month.

A pipeline is a named, saved workflow — the full graph of nodes, edges, and configurations, without the data. Loading a pipeline on a new dataset replays the entire workflow: the same transformations, the same schema mapping, the same analytical frames, the same export format. The only variable is the data.

localStorage (default)

Pipelines save automatically to the browser's localStorage under the meridian_pipelines key. They persist across sessions on the same machine. The pipeline library shows all saved pipelines with name, last-run date, and module target.

JSON export (portable backup)

Any pipeline can be exported as a .meridian JSON file. This file can be shared with a colleague, stored in a client folder, or version-controlled in a repo. Re-imported via the pipeline library in one click.

Pipeline data model

// A saved pipeline — what gets written to localStorage / JSON
{
  id:          "pipe_monthly_pricing_rev",
  name:        "Monthly Pricing Review — Renova",
  module:      "price",
  createdAt:   "2025-10-01T09:00:00Z",
  lastRunAt:   "2025-11-01T08:45:00Z",
  nodes: [
    { id: "n1", type: "source", config: { mode: "upload" } },
    { id: "n2", type: "filter", config: { expr: "[year] == 2024 AND [return_flag] == 0" } },
    { id: "n3", type: "calculate", config: { col: "pocket_price", expr: "[list_price] - [disc_amt]" } },
    { id: "n4", type: "schemaMap", config: { module: "price", map: { listPrice: "list_price", pocketPrice: "pocket_price" } } },
    { id: "n5", type: "analysis", config: { analysis: "pocket_price_waterfall" } },
    { id: "n6", type: "export", config: { format: "pdf", filename: "pricing_review_{date}" } }
  ],
  edges: [
    { from: "n1", to: "n2" }, { from: "n2", to: "n3" },
    { from: "n3", to: "n4" }, { from: "n4", to: "n5" },
    { from: "n5", to: "n6" }
  ]
  // No data — only the configuration. Data loads fresh each run.
}

What makes a pipeline portable: Because a pipeline stores node configurations and schema maps — never data — a .meridian file can be shared freely. A consulting manager can share their "Monthly Board Update" pipeline with a client's chief of staff. The client loads their own data. The analysis runs identically. This is consulting IP as a reusable workflow.

09 — AppHandoff Protocol

The interface contract between core and modules

Defined once, consumed by all. Any module that implements the receiver gets a fully prepared, quality-scored, schema-mapped dataset — without knowing what upstream operations produced it.

// AppHandoff — written to sessionStorage by Meridian Bridge
// key: 'meridian_handoff'
{
  source:       "Meridian Bridge",
  targetModule: "pulse",          // price | pulse | ledger | org | field | flow
  pipelineId:   "pipe_monthly_...", // null if ad-hoc
  sentAt:       "2025-11-01T08:45:00Z",
  rowCount:     45231,
  columns:      ["customer_id", "revenue_ltm", "last_purchase_date", ...],
  columnTypes:  { "customer_id": "id", "revenue_ltm": "number", ... },
  schema:       { "customerId": "customer_id", "revenue": "revenue_ltm", ... },
  qualityScore: 0.94,
  rows:         [{ ... }, { ... }]
}

Every module implements the four-method receiver interface: receiveHandoff(payload) → validateSchema(schema, required) → initModule(rows, schema) → renderOutputs(). Modules requiring Pyodide add a fifth: initPyodide() called asynchronously before initModule.

10 — Compute Model

Three tiers. Zero server. Full Python.

Vanilla JS
Aggregations, ratios, waterfall construction, sorting, filtering, basic statistics. Under 10K rows. Synchronous, instant. All modules, always.
All modules
Web Workers
Heavy tabular operations on datasets over 10K rows. Off main thread, non-blocking UI. Canvas pipeline execution also runs in a Worker.
>10K rows
Pyodide
Full Python runtime via WebAssembly. NumPy, pandas, scikit-learn, scipy, lifetimes. CLTV (BG/NBD), churn (logistic regression), propensity (gradient boosting), k-means clustering, ARIMA demand forecasting, survival analysis. Loads once, stays warm per session.
Pulse, Ledger, Org, Field, Flow · ML analyses

Scale ceiling: 50K rows is the comfortable zone for all analysis types including ML inference. The architecture scales to 500K rows for ETL/aggregations and 200K rows for churn/propensity inference without any architectural change — only a chunked file parser (already supported by PapaParse streaming mode) and mini-batch model variants. No server required at any scale within the defined operating range.

◈
Meridian Price
Phase 1 · live v1 · price/index.html
JS + Web Workers · Live

Commercial pricing intelligence workbench. Eight sub-modules covering the full pricing diagnostic sequence — from leakage identification through scenario modelling to deal-level scoring. Grounded in the Monitor Deloitte NAPA pricing transformation engagement.

Sub-modules

M1Pocket price waterfall — List price → invoice discounts → volume discounts → cash discounts → other allowances → pocket price → unit cost → gross profit. Heuristic 60/25/10/5 split when single discount column; exact mapping when separate columns are available. Leakage per element surfaced. M2Margin bridge — Period-on-period decomposition of gross margin change into volume effect, price effect, and mix effect. Configurable comparison periods and grouping dimension. M3Price-volume elasticity — Pearson correlation between discount % and units per transaction, scaled by SD ratio. Per-category and aggregate. Four interpretation bands. Framed as approximation — requires controlled price variation for true elasticity. M4Segment diagnostics — Average pocket price and discount % by customer tier, region, sales rep, or product category. Price band scatter overlay. Identifies non-uniform pricing beyond policy tolerance. Spread metric (max−min across segments) surfaced. M5Competitor benchmarking — Floor price (cost×1.10) and target price (list×0.90) computed from mapped data. Identifies products priced below floor (negative-margin) and below target (policy breach). M6Scenario modeller — Three parallel scenario branches on shared base data: (A) discount ceiling cap, (B) list price increase %, (C) floor price enforcement. Node-canvas shows the parallel pipeline structure. Revenue, profit, and margin delta per scenario. M7Deal scoring — Five-criterion scoring (0–100) per transaction: margin health (–30/–15), discount level (–25/–12), floor price compliance (–25), tier alignment (–10), extreme outlier flag (–15 additional). Score bands: <40 Flag · 40–70 Review · >70 Sound. M8Behavioural pricing lab — Always-on, data-free entry point. Interactive simulators: anchoring effect, decoy pricing, charm pricing, Good-Better-Best tier construction. No data upload required.

Required schema dimensions

Core (required): listPrice, pocketPrice, unitCost, discountPct or discountAmt, quantity. Enriching (optional): salesRep, customerTier, region, product, date. More dimensions mapped = richer segment diagnostics and margin bridge. Schema wizard auto-suggests from column name patterns.

Outputs

PDF report (all active analyses), XLSX per analysis (waterfall table, flagged deals list, elasticity by category), PNG chart exports. Scenario modeller: side-by-side scenario comparison table exportable as XLSX.

Compute

Vanilla JS for all analyses. Web Workers for datasets >10K rows (waterfall aggregation, deal scoring on large transaction sets). No model training required — all analyses are deterministic computations.

Demo dataset

Renova Home — 50 transactions, synthetic, with known signals: B2B contractor pocket prices ~18% below invoice, two sales reps with above-policy average discounts, category-level margin spread between own-brand and third-party SKUs.

Meridian Pulse
Phase 2 · live v1 · pulse/index.html
JS ML + Pyodide (Phase 2.1) · Live

Consumer analytics workbench. Seven sub-modules covering the full customer intelligence diagnostic — from RFM segmentation through CLTV projection, churn prediction, and propensity scoring. Grounded in the Mahindra AFS consumer analytics CoE engagement (~2M customer dataset, SQL Server).

Sub-modules

P1RFM segmentation — Percentile-ranked R/F/M scores (1–5) per customer across recency, frequency, monetary dimensions. Ten segment labels with explicit classification rules (Champions, Loyal, At Risk, Cannot Lose, Needs Attention, Hibernating, etc.). Runs automatically on data load — deterministic, no model training. P2CLTV model — DCF-based lifetime value projection. Purchase rate from actual frequency/tenure. User-configurable horizon (12/24/36 months) and discount rate (10–18%). Churn adjustment: 0.75× for recency 90–180 days, 0.50× for >180 days. Tier assignment at P25/P50/P75 quartiles of actual CLTV distribution — data-driven, not fixed thresholds. BG/NBD upgrade planned for Phase 2.1 (Pyodide). P3Cohort retention — Month-on-month retention curves by acquisition cohort. Requires transaction-level data for true computation; falls back to recency/tenure proxy with amber disclosure badge when summary data is loaded. P4Churn prediction — Logistic regression model trained in-browser via gradient descent (100 iterations, LR=0.1). Four features: normalised recency, inverse frequency, inverse monetary, binary inactivity flag (R≤2). Label: churned = recency >90 days AND R≤2. Fitted weights displayed dynamically post-training. Score bands: 0–40% Low · 40–70% Medium · 70–100% High. P5Propensity scoring — Deterministic weighted formula: 0.35×recency + 0.30×frequency + 0.20×monetary + 0.10×tenure + segment_bonus. Weights currently heuristic (PULSE-B01 — statistically derived weights planned for Phase 2.1). Decile assignment D1–D10. Output: ranked customer list with score and decile. P6Segment migration — Period-on-period RFM segment movement matrix. Shows how many customers moved from each segment to each other (e.g. Champions → Loyal, At Risk → Churned). Requires transaction-level data for true period-level computation. P7Acquisition vs retention mix — Revenue and customer count split between new (first purchase in period) and retained customers. Trend over time. CAC/LTV ratio surface. Proxy mode available when transaction data is not loaded.

Required schema dimensions

Summary mode: customerId, recency, frequency, monetary. Enriching: tenure, segment, acquisitionChannel, region. Transaction mode (required for P3/P6/P7): customerId, transactionDate, transactionAmount. Pulse auto-detects data mode on load.

Outputs

XLSX exports per analysis (RFM scores, CLTV scores, high-risk churn list, propensity ranked list). PDF report covering active analyses. Charts: RFM heatmap, CLTV distribution, churn risk histogram, propensity decile bar, cohort retention curves, migration matrix heatmap.

Compute

Vanilla JS for all Phase 2.0 ML (logistic regression gradient descent, DCF CLTV). Pyodide integration planned for Phase 2.1 (BG/NBD, statistically fitted propensity weights). All model training runs in-browser — no server, no upload, no API call.

Demo dataset

Renova Home — 100-customer summary file. Known signals: high-recency churn cluster among occasional purchasers, Champions concentrated in Tier 1 city stores, propensity D10 dominated by own-brand repeat buyers. Transaction-level dataset (~2,000 rows) pending (PLATFORM-B01).

13 — Design Principles

Eight principles — updated for canvas and pipelines

P1

The framework is the UI

Each module's interface is shaped by the analytical framework it embodies. The output is recognisable before the user reads a label.

P2

Canvas and panel are the same workflow

Switching views mid-workflow does not reset progress. The canvas renders the panel's state as nodes; the panel renders the canvas's state as steps. They are two representations of one data model.

P3

Schema mapping before analysis, always

No module runs analysis on unmapped data. The schema wizard is not skippable. This enforces methodological consistency — the output is always a real pocket price waterfall, not a chart on user data that someone labelled one.

P4

Outputs are deliverable-ready, not exploration-ready

The export target is a board deck or client presentation. Charts use consulting-grade colour and labelling. Tables include the metadata a reviewer needs. PDF export is a first-class feature.

P5

Complexity is hidden, not removed

BG/NBD and ARIMA run under the hood. The user sees the business output. Power users can inspect model parameters; everyone else gets the answer.

P6

Data never leaves the machine

Stated in every module's header as a factual architectural statement. This is also what makes the platform viable for consulting use — client data can be analysed locally without data governance implications.

P7

Each module is independently launchable

A module can receive a Bridge handoff or accept a direct upload. A user can bookmark Meridian Pulse, go directly to it, upload a CSV, and run a CLTV analysis — without opening Bridge at all.

P8

Pipelines are first-class IP

A saved pipeline is a consulting deliverable. It encodes the analytical methodology — the transformations, the schema map, the analytical frame — in a portable, reusable format. Sharing a .meridian file is sharing a workflow, not just data.

16 — Constraints & Scope Boundary

What Meridian is not

Immutable constraints: Zero server. Zero licence. Zero data leaves the user's machine. Single HTML file per module. CDN-only dependencies. These are architectural commitments. Any feature that violates them is out of scope by definition, regardless of how it is requested.

Explicit out-of-scope for v1.0

User accounts and cloud sync — no backend means no account system. Pipelines persist in localStorage and export as JSON. That is the persistence model.

Real-time data connections — no API integrations, no live database connections. Input is always a file upload or sessionStorage handoff.

Collaborative editing — one user, one browser session. Pipeline sharing is via .meridian file export, not a shared workspace.

Custom model training — Pyodide runs inference on pre-defined model architectures. Users cannot upload custom weights or modify model architectures. The ML layer is intentionally black-boxed.

Mobile-first design — desktop and laptop primary. Analytical tools at this complexity require screen real estate. Responsive layouts implemented, mobile not the primary experience.

The capstone outcome: When all six modules are live, Meridian will be the most comprehensive open-source browser-native analytical workbench for strategy and commercial consulting practitioners in existence. Alteryx-style canvas workflows. Reusable pipelines as shareable consulting IP. Full ML inference in-browser. Every module grounded in real engagement experience. Zero infrastructure. Permanent open access.

17 — Build Journal · Architecture ADRs

Five architecture decisions — with the reasoning that locked them

ADR-01Single HTML file per module — no build step, ever
Decision

Each module is a single self-contained HTML file. No bundler. No framework. No compilation step. No local toolchain dependency.

Why

A build step immediately excludes users who want to fork, inspect, and adapt. The product vision is consulting IP as open infrastructure — which means the IP must be readable by a developer with a browser and no installed tooling. GitHub Pages serves static files. A single HTML file deploys with zero configuration. Meridian Bridge is 4,500 lines, Meridian Price 2,600, Meridian Pulse 2,100 — large but legible.

Tradeoff accepted

As files grow, surgical edits risk breaking adjacent code. Mitigated by the CLAUDE.md session handoff protocol, which documents exact file locations, function names, and the four-method module interface contract before every Code session.

ADR-02Pyodide deferred — all Phase 2.0 ML in vanilla JS
Decision

Meridian Pulse ships with ML implemented in vanilla JS: logistic regression via gradient descent for churn, DCF-based CLTV, deterministic propensity scoring. Pyodide (browser Python) deferred to Phase 2.1.

Why

BG/NBD CLTV requires the lifetimes Python library — not in Pyodide's standard distribution. Loading Pyodide adds ~8MB WASM plus a 2–5 second initialisation penalty before the first ML call. For a consulting diagnostic tool where results need to appear in under 2 seconds, that is not acceptable for Phase 1. JS-implemented logistic regression with gradient descent produces genuinely fitted weights on the user's actual data in under 200ms. That output is analytically defensible in a client meeting. The upgrade path exists and is designed into the interface.

Upgrade path locked in

Phase 2.1. The four-method module interface already includes an optional initPyodide() call. The upgrade is additive — no structural change required.

ADR-03AppHandoff schema — immutable; additions allowed, removals not
Decision

The data contract between Meridian Bridge and all downstream modules is a fixed JSON schema written to sessionStorage under meridian_handoff. Existing fields cannot be removed or renamed. New fields can be added.

Why

All modules run in separate browser tabs with no runtime type checking. The only way to guarantee that adding Module 4 does not silently break Module 2 is to make the interface immutable at the field level. Adding new fields is safe because existing modules ignore unknown fields. The constraint is enforced by convention and documented in CLAUDE.md as a hard rule — not a preference.

ADR-04Pipeline storage — localStorage + JSON export, zero cloud
Decision

Named pipelines persist in localStorage under the key meridian_pipelines. Export format is .meridian (JSON). No cloud sync. No account system.

Why

The zero-server constraint eliminates cloud sync as an option. localStorage is the only browser-native persistence mechanism that survives page refreshes on the same device. The JSON export gives the portability that matters for the consulting use case: a consultant can share their "Q3 Pricing Review" pipeline with a client's finance lead as a file attachment. The client imports it, loads their own data, runs the same analysis. No account creation. No platform dependency. Pipelines as portable consulting IP — which is exactly the right model.

Limitation acknowledged

localStorage is per-device, per-browser, per-origin. Clearing browser data clears pipelines. The export prompt in the pipeline library is the explicit mitigation. This limitation is surfaced to users, not hidden.

ADR-05Canvas scoped to genuine pipelines only — removed from independent analyses
Decision

The Alteryx-style canvas exists in Meridian Bridge (where ETL is a true pipeline) and the Scenario Modeller in Meridian Price (where three scenario branches genuinely fan out from a shared base). It was added to Price and Pulse panel views and then removed.

Why it was removed from panels

In Bridge, the canvas represents real data flow — each ETL node transforms the output of the previous one. In the Price and Pulse panels, the eight and seven analyses respectively are independent — the waterfall does not feed the elasticity model. A canvas that draws arrows between independent analyses implies sequential dependency that does not exist. It is visually misleading. A misleading canvas is worse than no canvas. The panel UI is the correct interaction model for independent analyses.

Where canvas is correct

The Scenario Modeller in Price: base dataset fans out to three parallel transformation branches (discount cap, list price increase, floor price enforcement), each computing independently, converging on a comparison output. The branching structure is real. The canvas represents it accurately.

18 — Build Journal · Phase 0

Platform core — decisions and rationale for each component

Phase 0 was the prerequisite gate before any module could be built correctly. The three shared utilities (handoff.js, pipelines.js, canvas.js) were built before any module took a dependency on them — ensuring the interface contracts were stable before they were consumed.

handoff.js

AppHandoff protocol (163 lines)

Defines the data contract, column type inference, quality score helpers, schema validation, and module navigation utility. Made a shared file — not embedded in Bridge — because every module needs to read the handoff the same way. A single shared implementation prevents the interface contract from drifting across five or six independently-maintained modules.

pipelines.js

Pipeline engine (306 lines)

CRUD, topological sort (Kahn's algorithm), JSON export/import, pipeline library renderer. The topological sort was included even though all current pipelines are linear chains — because the node graph in Bridge can express non-linear dependencies, and building the correct data structure early costs nothing. Refactoring a linear sort into a topological sort later, after six modules have taken a dependency on the pipeline format, would be expensive.

Bridge

Meridian Bridge — DataBridge extended, not replaced

DataBridge v1 is live at its existing URL, used by people who arrived at it independently. The decision to leave it untouched and build Meridian Bridge as a separate working copy was deliberate. Original DataBridge = canonical standalone ETL tool. Meridian Bridge = extended version that knows it is part of a platform. Key additions: Meridian branding, privacy notice bar, module router replacing the old Pricing Analyser button, pipeline save, universal schema wizard covering all six module dimension sets, AppHandoff v2 payload, sessionStorage key migration from pa_incoming_dataset to meridian_handoff.

Also fixed a genuine usability bug in the original DataBridge: the delete (✕) button was only shown on result tables, not source tables. Source tables were unremovable without clearing all data. Fixed in Bridge — source tables now show the delete button on hover.

index.html

Platform home — module router and pipeline library

Reads directly from localStorage on load — no server call. Module cards that are not yet live show disabled state with "Coming soon." The home page requires no update when a new module launches — only the card's disabled state is toggled. Pipeline library renders saved pipelines from Bridge with run, export, delete, and import actions.

19 — Build Journal · Phase 1

Meridian Price — eight sub-modules, analytical methodology decisions

Meridian Price maps directly to the analytical sequence of the Monitor Deloitte pricing engagement. Every sub-module corresponds to a diagnostic that was run (or needed to be run) in the first four weeks of that project.

M1 — Pocket price waterfall · the 60/25/10/5 heuristic decision

When only one discount column is mapped, the waterfall splits it across four elements — invoice discount (60%), volume discount (25%), cash discount (10%), other allowances (5%) — using a heuristic grounded in the McKinsey pocket price methodology. This is documented explicitly in the UI. A heuristic waterfall with a clear disclosure is more useful than no waterfall. When the user maps separate discount columns, each maps to its own step exactly.

M3 — Price-volume elasticity · Pearson correlation, framed as approximation

Elasticity estimated via Pearson correlation between discount % and units per transaction, scaled by the ratio of standard deviations. True price elasticity requires controlled price variation — transaction-level sales data rarely provides this. The output is framed accordingly in the UI: "estimated from observed discount/volume correlation." Four plain-language interpretation bands translate the coefficient for a non-technical audience: strongly elastic, moderately elastic, moderately inelastic, highly inelastic.

M7 — Deal scoring · five criteria, exact threshold calibration

All thresholds calibrated to common commercial policy norms in B2B and retail distribution contexts. Criterion 1: margin below 20% triggers the largest penalty (–30 pts) because below that threshold, fixed cost absorption makes the deal structurally unprofitable. Criterion 2: discount above 25% (–25 pts) is the standard enterprise B2B maximum policy limit — above this, deals typically require VP+ approval. Criterion 3: pocket price below unit cost × 1.05 (–25 pts) — the variable-cost floor; below it, the deal is cash-negative. Criterion 4: B2B/SMB tier with discount above 20% (–10 pts) — B2B annual contracts mean per-transaction discounts above policy are a signal of unauthorised ad-hoc concessions. Criterion 5: discount above 30% triggers an additional –15 pts (the outlier tax). All criteria and thresholds are shown in a full table in the UI, with a worked example showing how penalties compound.

M6 — Scenario Modeller · why this is the only canvas in Price

Three parallel branches — discount cap, list price increase, floor price enforcement — each applying a different transformation to the base dataset and computing revenue, profit, and margin independently. The canvas here is justified because the branching is real data flow. The three scenario nodes genuinely fan out from a shared source and converge on a comparison node. This is structurally identical to how scenarios are modelled in a pricing war-gaming exercise — which is exactly what this module replicates.

M8 — Behavioural pricing lab · always-on, data-free entry point

The lab is the only module that requires no data. Anchoring, decoy pricing, charm pricing, and Good-Better-Best tiering are interactive simulators that let a user explore behavioural pricing mechanics before loading any transaction data. This was a deliberate design principle: the tool should be explorable before any data is loaded. A data-free entry point reduces the onboarding barrier and demonstrates the product's depth before any file is uploaded.

Run Analysis button pattern — why analyses don't execute on load

Initial build rendered all outputs immediately on navigation to a module. This was changed. The distinction between instant computations (deterministic, sub-100ms — RFM segmentation, waterfall) and model training or compute-intensive analyses (churn logistic regression, CLTV DCF projection, elasticity computation) is analytically meaningful and should be visible to the user. The pending state + explicit Run button makes this distinction legible. The button label changes on second run: "Re-run analysis" or "Re-train model." Auto-running vs user-triggered is enforced consistently.

20 — Build Journal · Phase 2

Meridian Pulse — consumer analytics methodology decisions

Meridian Pulse is grounded in the Mahindra AFS analytics CoE work — specifically the CLTV model on ~2M customers, the propensity scoring system, the cohort retention analysis, and the churn prediction model that was built on SQL Server. The browser-native version replicates that analytical capability set within the zero-server constraint.

RFM — percentile scoring, not fixed thresholds

RFM scores (1–5) are percentile ranks across the loaded customer base. Alternative: fixed absolute thresholds (e.g. "recency ≤ 30 days = R5"). Rejected because fixed thresholds are context-dependent — a 60-day-recency customer is highly active in a furniture business and dormant in a grocery business. Percentile scoring is self-calibrating: segments are always meaningful relative to this dataset. Segment labels (Champions, At Risk, etc.) follow explicit classification rules based on R/F/M score combinations, documented in the UI.

CLTV — DCF model for Phase 2.0, tier thresholds corrected mid-build

The DCF approach uses actual per-customer purchase rates (frequency ÷ tenure in months), projects forward over the user's chosen horizon (12/24/36 months), discounts each future period at the chosen annual rate (10–18%). Churn adjustment: customers with recency 90–180 days get 0.75× multiplier; over 180 days 0.50×. These are documented as heuristics in the UI, not presented as fitted parameters.

Tier thresholds were corrected mid-build. Original implementation used fixed absolutes (₹80K / ₹40K / ₹15K) — meaningless for datasets with different transaction scales. Corrected to P25/P50/P75 quartiles of the actual CLTV distribution. Tier 1 is always the top 25% of this customer base, regardless of absolute values. Each tier card shows the actual threshold range computed from the data.

Churn prediction — logistic regression, gradient descent, 100 iterations

Four features: normalised recency (0→1), inverse frequency (1 − freq/max_freq), inverse monetary (1 − spend/max_spend), binary inactivity flag (1 if R score ≤ 2). Training label: churned = 1 if recency > 90 days AND R score ≤ 2. Learning rate 0.1, 100 gradient descent iterations, sigmoid activation. After training, the fitted weights on the loaded dataset are displayed dynamically — the user sees actual relative feature importances (e.g. "Recency: 42% · Low frequency: 28%"), not a static diagram. A real model on real data, with its reasoning surfaced.

Propensity scoring — known limitation, backlog item PULSE-B01

Current formula: 0.35×recency + 0.30×frequency + 0.20×monetary + 0.10×tenure + segment_bonus. Weights are heuristic — informed by feature importance literature but not fitted to this specific dataset. Documented explicitly in the UI as such. Noise term removed mid-build (was adding (Math.random()-0.5)*0.05 to prevent ties — made scores non-deterministic). Scores are now fully deterministic: same data always produces the same scores. Statistically derived weights are backlog item PULSE-B01, planned for Phase 2.1.

Data mode detection — transaction vs summary, proxy disclosure

On load, Pulse detects data format: checks for date column, amount column, customer ID column, and whether unique customer ID ratio < 0.80 (multiple rows per customer). Transaction-level data enables true cohort computation. Summary data (one row per customer) triggers proxy mode for cohort retention, segment migration, and acquisition/retention mix — using recency and tenure as retention proxies. Proxy mode shows a clear amber badge on affected modules: "Customer summary data — cohort curves use recency/tenure proxy." The limitation is surfaced, not hidden.

Canvas

Canvas removed from panel views, retained only in Scenario Modeller

Implemented initially as a platform-wide toggle across all modules — a ▦ Panel / ◇ Canvas mode button in every topbar. The intended user presents Meridian outputs in board meetings and client reviews. They must be able to answer "how did you get this number?" without opening a notebook. Systematic pass added inline methodology notes across all Price and Pulse outputs: elasticity coefficient interpretation in four plain-language bands; deal scoring full criteria table with exact thresholds and worked example; CLTV DCF four-step breakdown with formula; churn model feature explanations plus dynamic fitted-weights display post-training; propensity formula with normalisation notes; RFM segment classification rules; waterfall heuristic disclosure; floor/target price derivation logic. Every number that could be questioned in a meeting has an accessible explanation one level down from the output itself.

Onboarding

Step indicator and guidance callouts added to both modules

Both Price and Pulse now have a step indicator in the context bar (Load data → Map schema → [Run segments/waterfall] → Run models → Export) that updates dynamically as each step completes — green when done, accent colour for active. Guidance callouts appear inline before each analysis pending state, explaining what the analysis does, what data it needs, and linking directly to the schema mapper where relevant. 22 — Build Journal · Bug Log

Every bug found and fixed — root cause first

Six of the seven bugs below share a single structural pattern: a render function that rebuilds its own UI on every call, overwriting state set by the user before reading it back. This is a consequence of the single-function render model — when one function handles both state-building and rendering, it resets what the user has changed.

BUG-01 · Elasticity category filter had no effect on the chart

Root cause: renderElasticity() called el.innerHTML = ... to rebuild the dropdown on every invocation, which reset the browser's .value property back to the first option before the function read it. The selected category was always 'all'.
Fix: Populate-once guard — if (el.options.length <= 1) before rebuilding. Dropdown resets and repopulates only when new data is loaded. User selection preserved across re-renders.

BUG-02 · Margin group and period filters — same root cause as BUG-01

Root cause: renderMarginBridge() also rebuilt its group dropdown and both period selectors on every call — same pattern.
Fix: Same populate-once guard. Period selectors also check options.length === 0 before populating.

BUG-03 · Segment diagnostics dimension filter resolved to wrong column

Root cause: dimCol = col(dimKey) || dimKey — the fallback used the schema key name (e.g. 'customerTier') when the dimension was not mapped, not the actual column name in the data. Filter compared row values against a non-existent column name, returning zero matches silently.
Fix: Added FALLBACK_COLS — a regex map that scans actual column names for a semantic match when schema is not mapped (e.g. /tier|segment|class|grade|loyalty/i for the customerTier dimension). If no match found, surface a toast directing the user to map the dimension rather than silently returning nothing.

BUG-04 · Propensity scores were non-deterministic

Root cause: A (Math.random()-0.5)*0.05 noise term was added to propensity scores to break ties in decile assignment. This made scores stochastic — the same customer could be D9 on one run and D8 on the next. Re-running the model on the same data would produce different ranked lists.
Fix: Noise term removed entirely. Scores are now fully deterministic. Ties are resolved by natural floating-point precision differences in the weighted formula.

BUG-05 · CLTV tier thresholds were fixed absolute values

Root cause: Tier boundaries hardcoded at ₹80,000 / ₹40,000 / ₹15,000. For a dataset where the top customer has ₹12,000 in CLTV, every customer lands in Tier 4. For a dataset where the average is ₹200,000, every customer is Tier 1. The thresholds carried no meaning relative to the actual distribution.
Fix: Thresholds now computed as P25, P50, and P75 of the actual CLTV distribution from the loaded dataset. Tier 1 is always the top quartile of this customer base. Each tier card shows the actual computed threshold range.

BUG-06 · Run Analysis button rendered as unstyled default (black text, white background)

Root cause: The .run-analysis-btn CSS class was used across both Price and Pulse modules but was only defined in the Price stylesheet. When the Pulse file was built from the phase3-fix build, the CSS block was not carried over. The browser applied zero custom styling, rendering the button as a native default OS button.
Fix: CSS block injected into Pulse with full styling — module accent colour background (#a78bfa), dark text (#0d1117), hover state, disabled state, spinner animation.

BUG-07 · Pulse file truncated during canvas-stripping regex pass

Root cause: A Python re.sub() call with the DOTALL flag was used to strip the canvas JS block. The regex pattern matched beyond the intended end of the canvas block, consuming the closing </script></body></html> tags and the run model functions that had been injected in a previous pass. The file was written back truncated — no closing HTML tags, no run functions.
Fix: Detected by checking for </html> presence and counting run function references. Closing tags and run functions appended. Regex patterns narrowed with more specific end anchors to prevent recurrence.

Known limitations and what is planned to address them

PULSE-B01Propensity weights should be statistically derived, not heuristic
Current weights (0.35 recency / 0.30 frequency / 0.20 monetary / 0.10 tenure) are informed by consumer analytics literature but not fitted to the specific dataset. The correct approach treats propensity scoring as a supervised learning problem: label each customer-period pair as purchased=1 or not=0, run logistic regression or survival analysis to fit coefficients, use those as weights. Requires transaction-level data and consumer analytics reference texts (being sourced). Planned: Phase 2.1.
PULSE-B02CLTV model upgrade to BG/NBD + Gamma-Gamma with Pyodide
BG/NBD is the correct probabilistic model for non-contractual consumer businesses — it models the alive/dead latent process and heterogeneous purchase rates. Gamma-Gamma models the monetary value conditional on a purchase. Both are available via the lifetimes Python library. Requires Pyodide integration. Module interface already includes the optional initPyodide() hook — upgrade is additive. Planned: Phase 2.1.
PRICE-B01Waterfall multi-column discount decomposition
Schema wizard currently supports mapping one discount amount column. When a user has separate invoice discount, volume discount, cash discount columns, these should each map to their own waterfall step — eliminating the 60/25/10/5 heuristic split. Requires a schema wizard extension for sub-type discount mapping. Planned: Price v1.1.
BRIDGE-B01Source table delete needs a confirmation prompt
The delete button now appears on source tables (Phase 0 fix for DataBridge usability gap). However, deleting a source table is irreversible within the session — the data came from a file. A confirmation prompt is required before execution: "Remove this dataset? This cannot be undone in the current session." Planned: Bridge v1.2.
PLATFORM-B01Renova Home transaction-level dataset for Pulse cohort analyses
Current Renova customer dataset is a 100-customer summary file (one row per customer). Cohort retention, segment migration, and acquisition/retention mix analyses require event-level transaction data (one row per purchase event) to compute true cohort curves. A transaction-level Renova dataset of approximately 2,000 rows across 18 months is needed to demonstrate these analyses running in full computation mode rather than proxy mode. Planned: before Phase 3.
